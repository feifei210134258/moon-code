# Moon Code 0.2.0 PRD：次主力模型

状态：实现与验收完成，待用户确认
版本：Moon Code `0.2.0`
创建日期：2026-07-27
关联文档：[Kimi Code 次主力模型配置说明](https://moonshotai.github.io/kimi-code/zh/configuration/config-files.html#secondary-model)

## 1. 迭代目标

在 Moon Code 中接入 Kimi Code 的 `secondary_model` 能力，使新派生的 `Agent / AgentSwarm` 可以默认使用一个成本更低或职责不同的模型，同时保留主 Agent 使用 primary 模型的能力。

本迭代是一次独立的 Runtime 能力升级，不假设项目永久绑定 Kimi Code `0.29.0`。当前机器上的系统 Kimi CLI 已升级到 `0.29.2`；项目内托管依赖、契约快照和版本门禁需要在本迭代中重新验证并按实际支持情况更新。

## 2. 用户价值

- 主 Agent 继续使用高能力模型处理复杂推理和最终决策。
- 子 Agent 默认使用更便宜、更快或更适合探索任务的模型。
- 用户可以在 Moon Code 设置中看到和修改次主力模型，而不需要手工编辑 Kimi 配置文件。
- 用户可以直接复用 Kimi 内置模型，或在同一区域连接任意 Kimi Code 支持的 Provider，再刷新并选择该 Provider 的模型。
- 次主力模型的 effort 与模型能力联动，避免发送无效的 thinking 参数。
- Runtime、配置错误和实验功能状态对用户可见，不静默降级。

## 3. Kimi 官方语义（必须保持）

### 3.1 配置结构

```toml
[secondary_model]
model = "kimi-code/kimi-k2.5"
default_effort = "low"
max_output_size = 8192
```

- `model` 必须引用已配置的 `[models]` 条目。
- 模型可以来自任意 Provider，不限于 Kimi Provider。
- `default_effort` 的解析链路为：次主力模型配置 → 全局 `[thinking]` → 模型默认 effort。
- `model` 以外的字段是只对子 Agent 生效的模型补丁。
- 有补丁时，Runtime 在内存中创建派生模型；该条目不会写回 `config.toml`，也不会出现在模型选择列表中。
- 未设置 `secondary_model` 时，新派生子 Agent 继承主 Agent 模型。

### 3.2 实验开关和优先级

- `kimi web` 需要 `KIMI_CODE_EXPERIMENTAL_SECONDARY_MODEL=1`。
- `kimi -p` 的 v2 引擎需要 `KIMI_CODE_EXPERIMENTAL_FLAG=1`；Moon Code 主路径是 `kimi web`，优先实现前者。
- 交互式 TUI 忽略该配置。
- `KIMI_SECONDARY_MODEL` 覆盖配置文件中的 `model`。
- `KIMI_SECONDARY_EFFORT` 覆盖配置文件中的 `default_effort`。
- 模型无法解析或 effort 不合法时，Runtime 在启动阶段发出警告；派生子 Agent 时仍可能失败，客户端必须保留错误来源。

## 4. 当前基线和差距

### 4.1 当前基线

- 本机系统 CLI：Kimi `0.29.2`。
- 项目内依赖：`@moonshot-ai/kimi-code@0.29.2`。
- 当前最低支持版本：`>=0.29.2`；未来版本不设硬上限，具体功能通过 Runtime 契约和 capability 探测开放。
- Moon Code 通过官方 Kimi Web REST/WebSocket 接入，不直接读取或修改 `config.toml`、凭据或 Session 文件。
- `/api/v1/config` 的 GET/POST merge 已经由 [KimiRestClient.ts](../packages/kimi-adapter/src/transport/KimiRestClient.ts) 提供。

### 4.2 需要补齐的能力

- 重新确认 Kimi `0.29.2` 及后续版本是否真的支持 `secondary_model`。
- 托管 Runtime 启动时注入实验环境变量。
- 对共享 Runtime、系统 Runtime、外部 Runtime 区分“已启用 / 未启用 / 未知”。
- 将 `secondary_model` 纳入 typed schema、Main bridge、IPC 和 Renderer 设置。
- 次主力模型候选必须覆盖所有 Provider。
- 处理配置清除（unset）语义，禁止通过全量回写或直接改文件实现。

## 5. 产品范围

### P0：本版本必须完成

#### SM-001 Runtime 版本和契约升级

- 使用当前系统 Kimi CLI `0.29.2` 做真实探测。
- 重新捕获目标版本的 OpenAPI/AsyncAPI/config schema，并更新契约快照。
- 如果能力只在更高版本提供，升级托管依赖和支持范围；不得因为当前依赖固定为 `0.29.0` 而阻塞后续版本。
- 对不支持该能力的 Runtime 显示兼容性提示，并保持现有主模型流程可用。

#### SM-002 实验开关管理

- Moon Code 启动自己托管的 `kimi web` 时注入 `KIMI_CODE_EXPERIMENTAL_SECONDARY_MODEL=1`。
- 不把环境变量暴露给 Renderer；用户确认后可通过类型化 IPC 重启 Moon Code 自己启动的 Runtime。
- 共享 Runtime 或外部 Runtime 无法确认开关状态时，显示“状态未知”，不假设已启用。
- 需要重启 Runtime 才能生效时，设置页明确提示；不得自动终止用户正在使用的共享 Runtime。

#### SM-003 Typed Config / IPC

- Settings snapshot 增加次主力模型配置、能力状态和警告信息。
- 新增类型化的读取、更新和清除操作。
- 校验模型 ID、effort、数值边界和允许的 override 字段。
- 保持 API key、OAuth 引用和完整 raw config 不进入 Renderer。
- 优先使用官方 `/api/v1/config` 写能力；在 `0.29.2` 中使用官方 secondary 环境变量作为 Moon Code-owned Runtime 的启动覆盖，不能直接改文件。
- “禁用”通过 `KIMI_CODE_EXPERIMENTAL_SECONDARY_MODEL=0` 实现，不伪装成删除 Kimi 配置文件中的 `[secondary_model]`。

#### SM-004 Settings UI

- 在模型设置中增加“次主力模型（实验）”区块。
- 模型候选来自所有已配置 Provider。
- 次主力模型按“Provider 连接 → 获取模型列表 → 选择模型”呈现，不把它误解为 Kimi 专属模型开关。
- 内置 Kimi Provider 直接可选；已有自定义 Provider 可复用并刷新模型目录。
- 新增 Provider 至少提供 Provider ID、协议类型、Base URL 和 API Key；API Key 只经 typed IPC 交给 Kimi，Renderer 不回读、不展示。
- 连接 Provider 后调用 Kimi 官方刷新接口获取模型列表；Moon Code 不直接请求第三方 `/models`，也不建立第二份 Provider 配置。
- 根据所选模型的 `support_efforts` 动态显示 `default_effort`。
- 支持已验证的模型补丁字段，首版至少包括 `max_output_size`。
- 显示以下状态：已启用、未启用、状态未知、不支持、需要重启、配置警告。
- 清晰说明：只影响新派生的 Agent/AgentSwarm，不改变主 Agent 和已有 Agent。

#### SM-005 Agent 行为对等

- 不在客户端自行重写子 Agent 的模型选择；primary/secondary 选择仍由 Kimi Runtime 负责。
- 真实 Runtime 验证新派生 Agent 默认使用 secondary，未设置时继承 primary。
- 如果上游事件提供实际模型或 effort，在 Agent Detail 中展示；上游未提供时不推测、不伪造。

#### SM-006 测试和验收

- 单元测试覆盖 schema、映射、IPC 校验、环境变量优先级和 warning。
- 真实 Runtime 测试覆盖 secondary、继承 primary、错误模型、错误 effort、unset 和 Runtime 重启。
- 所有常规检查通过 `pnpm check`。
- 真实 Kimi 集成测试必须显式 opt-in，不得让普通 CI 依赖用户账号或本机 Runtime。

### P1：条件允许时完成

- Agent roster 展示实际模型、来源（primary/secondary）和 effort。
- 高级设置支持更多已确认的模型 override 字段。
- 对跨客户端 `event.config.changed` 的 secondary 配置变更做端到端刷新验收。
- 设置页提供“复制等价 TOML 示例”，但只读展示，不允许客户端绕过 Kimi Server 写文件。

### 明确不做

- 不建立第二套 Agent 或聊天数据库。
- 不在 Renderer 直接访问 Kimi REST/WebSocket。
- 不直接编辑 `~/.kimi-code/config.toml`。
- 不把 secondary 模型硬编码成某一个 Kimi 模型。
- 不在 Moon Code 内实现一套替代 Kimi Runtime 的子 Agent 调度器。
- 不把 TUI 宣称为支持 secondary_model。

## 7. 验收场景

### 场景 A：启用次主力模型

1. 用户可选择内置 Kimi Provider、已有 Provider，或输入 API Key / Base URL 连接新 Provider。
2. Moon Code 通过 Kimi 官方配置与刷新接口获取该 Provider 的模型列表。
3. 用户选择模型和该模型支持的 effort。
4. 保存后看到“仅新派生 Agent 生效”的提示。
5. 新 Agent/AgentSwarm 使用 secondary；主 Agent 仍使用 primary。

### 场景 B：未配置次主力模型

1. 用户选择“禁用并恢复继承主模型”。
2. Moon Code 保存本机 Runtime 启动偏好并提示需要重启。
3. 重启后的 Moon Code-owned Runtime 使用 `KIMI_CODE_EXPERIMENTAL_SECONDARY_MODEL=0`；新派生 Agent 继承主 Agent 模型。
4. Kimi `config.toml` 中可能存在的 secondary 配置不会被删除，UI 必须明确区分“Moon Code 中已禁用”和“Kimi 持久配置仍保留”。

### 场景 C：环境变量覆盖

1. 配置文件设置模型 A。
2. `KIMI_SECONDARY_MODEL` 指向模型 B。
3. UI 显示“由环境变量覆盖”，实际 Runtime 使用模型 B。

### 场景 D：共享 Runtime

1. Moon Code 连接已运行的共享 Kimi Web Runtime。
2. 客户端无法确认实验开关状态时显示“状态未知”。
3. 不自动重启共享 Runtime，不误报“已启用”。

### 场景 E：配置错误

1. secondary 指向不存在的模型，或 effort 不受支持。
2. 启动时显示来源明确的 warning。
3. 派生失败时保留 Kimi Runtime 原始错误语义。

## 9. 当前决策记录

1. 0.2.0 是独立迭代，不把 Kimi `0.29.0` 视为永久版本上限。
2. 当前系统 CLI `0.29.2` 作为第一验证目标。
3. Moon Code 继续以 Kimi 官方 Web REST/WebSocket 为唯一 Agent 内核。
4. secondary 配置必须走官方 Kimi REST 或文档明确支持的环境变量；不能通过本地文件编辑绕过 Server。
5. 实验功能默认不改变当前用户行为，只有 Runtime 能力确认并显式启用后才生效。
6. Kimi 版本只设置最低门槛，不设置 `<0.30.0` 等未来版本硬上限；破坏性变化由契约探测和功能级 capability 隔离。
